x86-64 · C + no_std Rust · MIT · research-grade

A microkernel where authority is held, never assumed.

Horus treats the capability — an unforgeable token naming one object and one set of rights — as its single foundational security primitive. Every privileged operation goes through one. There is no root bit that opens every door and no ambient "the caller is trusted" path: a task can only do what it holds a capability for, and can only delegate a subset of what it holds.

It boots on x86-64 hardware and under QEMU, drops to a ring-3 shell, and runs ordinary C programs — GNU coreutils and the Tiny C Compiler — on a kernel whose filesystem and console driver live in userspace. The build is byte-for-byte reproducible, the boot chain is measured into a TPM, and the volume encryption key is sealed against those measurements.

Overview

A C kernel with a security core the compiler can check.

The kernel is C. The security core is no_std Rust compiled to a static library and linked into it. The split is drawn by attack surface, not by convenience: code that parses attacker- or firmware-controlled bytes, or that enforces an algebraic security property, belongs in Rust. Today that means the capability algebra, ELF header and relocation parsing, the cryptographic primitives, the ChaCha20 CSPRNG, the pointer and range validation predicates, and the forward-secure audit log.

That split is argued empirically, not aesthetically: moving the ELF loader to Rust found two real out-of-bounds bugs in the C original. The C/Rust ABI is pinned by mirrored compile-time assertions on field offsets on both sides of the boundary, so layout drift is a build failure rather than a silent reinterpretation of memory, and cargo-fuzz runs over the predicates at that boundary.

The trusted computing base is roughly 20 kLOC of kernel, plus init (the delegation root), fs_server (the filesystem reference monitor), console_server (which sees all terminal traffic), and the firmware below measured boot. The shell, coreutils, TCC and every user program are outside it by design.

The model

Authority is a graph, and the kernel is the only thing that can draw an edge.

A capability is {type, rights, object, badge, serial, generation}. It lives in a per-task 256-slot capability space and is named only by slot index — userspace never sees the struct, so it cannot be forged or guessed.

Delegation only narrows

Mint derives a child with rights & new_rights. Grant pushes a capability into a child the caller supervises — downward, never upward. Widening is not a policy the kernel declines; it is an operation that does not exist.

cargo test · Kani

Revocation is subtree-scoped

SYS_CAP_REVOKE nulls the target and everything transitively derived from it, across every task's capability space, while leaving ancestors, siblings and independent capabilities to the same object intact.

Kani proof · smoke-captest

Two independent backstops

Each capability's serial keys a generation cell bumped on revoke, so a detached snapshot of a revoked capability fails validation even if the structural sweep somehow missed it. Both mechanisms must hold.

cargo test

IPC is capability-addressed

Every IPC syscall's first argument is a capability slot, not an object index. One choke point checks the capability's type, the right for the direction, and its lineage before object is trusted at all. READ is the receive right — it is what separates a server from its clients, and clients are minted WRITE-only.

smoke-captest — twelve checks

Replies cannot be forged

SYS_IPC_RECV mints a one-shot CAP_REPLY naming the sender of the message it dequeued; SYS_IPC_REPLY_TO requires it and consumes it. Replying to a client you never heard from, replying twice, or replying to the wrong client are not refused — they are unrepresentable.

smoke-captest — four checks

Kernel objects come from untyped memory

A CAP_UNTYPED names a region of physical memory and SYS_RETYPE carves typed objects out of it, following seL4. A task holding no untyped capability cannot create a kernel object at all, and the region it does hold is a hard bound on the kernel memory it can consume.

smoke-captest — twenty-two checks

Bytes are never reused under a stale name

Allocation inside a region is a monotonic bump pointer. Destroying an object does not return its bytes, so they become reusable only once every capability into the region is gone — the same event that invalidates the stale reference. Type confusion through reuse is structurally impossible rather than merely avoided.

docs/ARCHITECTURE.md §4

Object lifetime follows the graph

A retyped endpoint or notification exists exactly as long as some capability names it, computed by mark-and-sweep over the capability graph rather than by a refcount — so reachability and the security argument are derived from the same structure and cannot disagree.

smoke-captest

Zero-trust identity

A server never trusts what a client says about itself. SYS_IPC_SENDER returns the uid the kernel recorded for a message's sender, established only by a successful login. fs_server authorises every file operation against that value.

smoke-fs-perms

This is the part of the system that changed most recently, and it changed because an audit found it wanting. Until 2026-07-27, IPC endpoints were addressed by a raw integer index and the dispatch table gated IPC on a capability slot every task happened to hold — so any ring-3 task could intercept or forge messages to any userspace server. That finding (C-1) is fixed, and the conformance suite that missed it was rebuilt and then falsified against the vulnerable kernel to prove it now detects the bug.

Boot chain

Three layers between firmware and a mounted volume, each tested adversarially.

Module integrity

A SHA-256 manifest of every boot module is generated at build time and compiled into the kernel image. Each module is hashed at boot and compared; a mismatch makes the module unreadable, and since provisioning into /bin goes through that read path, an unverified module can never become a root-owned executable.

smoke-modules-tamper — corrupts a payload inside the ISO

Measured boot

The kernel image and each module are extended into TPM 2.0 PCR 8 and 9 over the TIS interface. A host-side script recomputes the expected values independently, and CI asserts they match.

smoke-tpm · smoke-tpm-tamper

Sealed volume key

The vdisk key-encryption key is sealed to those PCRs under a PolicyPCR session. A measured-good boot unseals it; any change to the kernel or modules changes the PCRs and the volume stays locked.

smoke-tpm-seal · smoke-tpm-seal-roundtrip

Encryption at rest

Per-(inode, block) AEAD subkeys — ChaCha20 for confidentiality, HMAC-SHA256 for integrity — with a fresh nonce per write and a hierarchical rollback MAC over block metadata. The AEAD stays entirely in the kernel; the ring-3 filesystem server never sees a key.

smoke-fs · RFC test vectors

Reproducible build

make reproducible-build builds twice and diffs kernel.elf. It is a required CI check — one of the few security-relevant gates that actually blocks a merge.

required status check

Verified inbound dependency

The one network dependency in the build path — the newlib tarball — is pinned by SHA-256, verified on every invocation rather than only after a fetch, refused before unpacking, and quarantined rather than left in place when it fails.

Method

Test that the control fires, not that the happy path works.

Horus's security argument rests on its tests, so they are treated as engineering artifacts rather than an afterthought. Three layers: Rust unit tests and Kani proofs on the host; 30+ QEMU integration self-tests that boot a purpose-built kernel and assert a serial marker; and scripted sessions that type into the real ring-3 shell over serial.

A test that cannot fail on the bug it targets is not evidence

Every gate here is falsified before it is trusted: the defect is reintroduced deliberately and the suite must go red. This is not ceremony. The first draft of the capability conformance suite asserted < 0 rather than the exact error code — and passed with the vulnerable IPC handler restored, because sys_ipc_recv returns -2 for an empty mailbox and a negative return could not distinguish "the kernel refused me" from "I was allowed to read, and nothing was there". The suite now asserts exact codes, and every new syscall must ship with a negative test.

Falsification runs in both directions where it can. A refusal-only suite would be passed by a kernel whose SYS_RETYPE returned "permission denied" unconditionally, so the untyped-memory checks also assert that a held capability really does create usable, mutually distinct objects. One check was renamed after falsification showed it did not test what its name claimed — a green check whose name overstates it is a worse artifact than no check, because it is a claim nobody will re-derive.

A single green run is not evidence about a concurrency change

Intermittent failures are quoted as rates over pinned boots, never as one passing run. The reason is specific: under QEMU's TCG each guest vCPU is a host thread, so on an idle many-core workstation the scheduling windows never open and a failing kernel scored 10/10 green. The bug only appears where vCPUs outnumber host cores — which is what a CI runner is. Stress harnesses build once and then boot the same ISO N times with QEMU pinned to a small host CPU set.

Sample size is part of the argument, not a detail. A 30-boot run witnesses a 2% event less than half the time; when the scheduler's claim invariant needed to be excluded as a cause, the run was 150 pinned boots, all passing, which is what made the exclusion sound.

"Flaky" is a hypothesis, not a diagnosis

This project has been wrong in both directions and documents both. smoke-console-smp failed about a third of the time for months and was treated as noise; it was correctly reporting an intermittent kernel deadlock. Later, a scheduler invariant checker accused a correct kernel of a claim leak and blocked a roadmap item for a fortnight — the checker's model of "what this CPU is running" was the thing that was wrong. A checker that reports a violation is making a claim about the code, and it can be the one at fault.

Adversarial gates

smoke-modules-tamper corrupts a module payload inside the ISO and asserts refusal. smoke-tpm-tamper asserts the measured PCRs additionally diverge — detection as well as prevention. smoke-newlib-tamper asserts a tampered libc tarball is refused before unpacking, and that the genuine one still passes, because a gate that refused everything would sail through the negative control alone.

A gate must assert the property it is named for

The scheduler-invariant stress job originally failed on any failed boot, so an unrelated hang reddened a job whose entire claim is "the claim invariant holds". It now fails on the panic it exists to catch and reports anything else loudly without gating. Likewise the SMP soak once trusted an exit status alone — a session test that degraded into a no-op would have reported green over boots that tested air, so each run must now also clear a minimum check count or be reported as vacuous.

Open

Known limitations and open findings.

Horus is research-grade, not production-ready, and has not been independently audited. These are the ones worth knowing before you draw a conclusion about it; the full, deliberately unflattering account is in LIMITATIONS.md.

  • G-8 — the SMP session soak is not clean, and the mechanism is not established

    smoke-session-smp-soak fails at roughly 2–3% per boot on current main. Distinct signatures have been captured, one of which matches a previously fixed deadlock verbatim, so the open question is whether that fix is incomplete or a second defect presents identically. The CI job is advisory, not gating — at that rate a required check reddens about a third of runs and simply teaches everyone to press re-run, which is the reflex that hid the earlier deadlock for months. That is a mitigation, not a fix. Signatures are recorded; a mechanism is explicitly not claimed.

  • The spinlock's interrupt state is global, and the bug is load-bearing (C-3, C-3.1)

    The IRQ nesting depth is a single global counter shared by every CPU, and spin_unlock issues an unconditional sti. Because that fires for any lock taken while interrupts were already masked, the ring-3 startup handshake depends on preemption that is a consequence of the defect rather than of any stated policy. A correct per-CPU lock was written, passed every local gate, broke the handshake in CI, and was reverted. Roadmap 1.1 now has its first two steps done — an audit mode that identifies the depth-zero releases enabling interrupts the caller had masked, over seven sites, every one of them a syscall-context lock user, and smoke-irq-policy, which records interrupt state at five named boot milestones and gates on it. The lock itself is step three and has not landed.

    The audit's published totals are being re-derived and are omitted here on purpose. The counts are cumulative and depend on how long the sample ran, and the figures previously quoted turned out to be the frozen counters of a boot that had stalled — the instrument also perturbs the session it measures. The seven sites reproduce; the totals did not survive re-measurement.

  • The write-ahead journal is not durable on real hardware (I-10, I-11)

    The ATA driver issues READ, WRITE and IDENTIFY — there is no FLUSH CACHE anywhere in the kernel, so on real hardware the journal's commit record can sit in the drive's volatile write cache and be lost to a power failure. This is invisible to the test suite, because smoke-fs-wal runs QEMU with cache=writethrough, where the emulator supplies the durability the kernel omits. Treat filesystem crash-atomicity as demonstrated under emulation, unproven on hardware. That same test is also nondeterministic by construction and is a required check, so it can block merges spuriously.

  • IPC receive still polls

    Endpoints are bounded FIFO queues and reply capabilities are one-shot, but SYS_IPC_RECV still returns "would block" on an empty queue rather than sleeping. A server with no work spins instead of blocking, and priority inheritance remains inexpressible. That is the last remaining piece of roadmap 1.3.

  • Security tests do not gate merges (C-6)

    Of roughly 30 CI jobs, 21 are required status checks — and the security-specific ones are not among them. Capability conformance, kernel W^X, measured boot, boot-module tamper rejection, SMEP/SMAP presence, flush-on-switch and stack-guard reseed can all fail while a pull request merges green. The required set is inverted: functional tests block merges, security tests do not.

  • No independent review (C-5)

    Horus is maintained by one person and recent pull requests merged with zero reviews. The assurance it can honestly claim is "thoroughly automatically verified", not "independently reviewed". The IPC finding is the demonstration of what that combination produces: a defect that passed every automated gate, because the suite tested the property the author had in mind rather than the property the documentation claimed.

  • The cryptography is unaudited

    Every primitive — ChaCha20, SHA-256, BLAKE2b, Argon2, the AEAD — is a from-scratch no_std Rust implementation checked against published test vectors. None has been independently audited and none is verified constant-time. Treat them as research code.

  • Smaller sharp edges, all tracked

    User copies clamp and return success rather than refusing (C-4). The heap syscalls do 32-bit arithmetic on 64-bit bounds — latent until the user address space widens past 4 GiB (I-2). The revocation worklist is bounded at 256 entries and over-approximates on overflow, which an unprivileged task can force as a denial of service against a peer's independent capability to the same object (I-3). There are no tagged releases, no signed artifacts and no SLSA provenance, so a third party cannot verify that a boot.iso came from this repository's CI (I-9). Formal verification is narrow: Kani covers revocation, and the TLA+ specifications are committed but not model-checked in CI.

Where the line sits

Horus boots, runs a ring-3 init that supervises a ring-3 shell, and enforces capability-based access control end to end, including across the IPC namespace. The infrastructure around it — reproducible builds, measured boot, adversarial CI, formal proofs — is substantially more mature than the kernel it verifies.

This is a research and learning kernel, not a shipping OS. It has not been audited by a third party, and nothing here should be trusted with anything real.

Verify

Don't take the tables' word for it.

Every claim above is a command you can run. x86-64 Linux host, Debian or Ubuntu; no cross-compiler needed. 

# build and boot
$ rustup target add x86_64-unknown-none
$ make              # kernel.elf
$ make run          # boot.iso + QEMU
                    # console is this terminal;
                    # Ctrl-A X quits QEMU
$ make run-tpm      # with an emulated TPM (swtpm)
# prove it
$ make test                  # the full local sweep
$ make smoke                 # boot to the ring-3 login
$ make smoke-captest         # 88 capability checks
$ make smoke-modules-tamper  # corrupt a module, expect refusal
$ make smoke-tpm-seal        # changed PCR ⇒ volume stays locked
$ make reproducible-build    # build twice, diff kernel.elf

Log in as root / horus, then try ls /bin, dmesg, ps, man hier, tcc -v, or cat /etc/motd | wc -l. Every target, every configuration flag and the troubleshooting notes are in BUILDING.md; what each test proves — and where the suite has been wrong before — is in TESTS.md.

Next

Ordered by assurance value, not by demo value.

A feature built on an unenforced foundation adds surface without adding capability, and raises the cost of fixing the foundation later.

Track 0 — make the object model true — is complete. IPC is capability-addressed, ambient uid == 0 authority is retired, and creating a kernel object is an exercise of authority the capability graph describes.

Track 1 is the current work: making boot-time interrupt enablement explicit and then landing the per-CPU, interrupt-preserving lock; a blocking receive to finish the IPC primitive; fail-closed user copies; 64-bit-clean heap arithmetic; a durable journal; and an unbounded revocation closure. Track 2 grows the OS on top of that — frame capabilities and shared memory, a monotonic clock and timers, a real process and session model, a VFS, dynamic linking, and a network stack as a ring-3 server holding one NIC's capability.

The single highest-leverage change is not technical. It is finding a second reviewer for the capability paths; automated verification has already been pushed about as far as it goes without one. The full plan, with rationale and security impact per item, is in ROADMAP.md.
